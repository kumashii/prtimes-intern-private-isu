# PR TIMES インターン選考課題

PR TIMESのインターン選考課題として、Webアプリケーション `private-isu` のPHP実装を対象に、ベンチマークを計測しながらパフォーマンス改善を行いました。

## 使用環境

- PHP
- MySQL
- nginx
- memcached
- Docker / Docker Compose

---

変更前の状態でベンチマークを実行しました。

- success: 985

この結果を基準として、SQLやアプリケーションコードを確認しながら改善を行いました。

# 改善① コメント検索用インデックスの追加

## 問題

投稿に紐づくコメントを取得する処理で、`comments` テーブルに適切なインデックスがなく、多くの行を走査していました。

`EXPLAIN` を確認すると、約10万件のデータを対象に検索していることが分かりました。

## 改善内容

`comments` テーブルに以下の複合インデックスを追加しました。

```sql
(post_id, created_at)
```

これにより、

- 投稿IDによる絞り込み
- 作成日時による並び替え

をインデックスを利用して処理できるようにしました。

また、環境を再構築した場合でも変更が反映されるように、SQLファイルとしてインデックス追加処理を残しました。

## 結果

改善前：

- score: **966**

改善後：

- score: **9148**
- success: 8279
- fail: 0

大幅なスコア向上を確認できました。

# 改善② ユーザー情報の重複取得を削減

## 問題

投稿一覧を生成する `make_posts()` 内で、投稿者やコメント投稿者のユーザー情報を取得するために、

```sql
SELECT * FROM users WHERE id = ?
```

が繰り返し実行されていました。

同じユーザーが複数回登場した場合でも、その都度MySQLへ問い合わせていたため、不要なDBアクセスが発生していました。

## 改善内容

`make_posts()` 内にユーザー情報のキャッシュを追加しました。

一度取得したユーザー情報をPHP側に保存し、同じユーザーIDが再度必要になった場合はDBへ問い合わせず、キャッシュした情報を利用するように変更しました。

```php
$user_cache = [];

$get_user = function ($user_id) use (&$user_cache) {
    if (!array_key_exists($user_id, $user_cache)) {
        $user_cache[$user_id] = $this->fetch_first(
            'SELECT * FROM users WHERE id = ?',
            $user_id
        );
    }

    return $user_cache[$user_id];
};
```

## 結果

3回ベンチマークを実行しました。

- 8532
- 10653
- 11071

中央値：

- **10653**

すべて `fail: 0` で正常動作を確認しました。

改善①の `9148` と比較して、さらに性能が向上しました。

# 改善③ 不要な全件取得とPHP側の集計を削減

## 問題

コードを確認すると、画面に表示する投稿数は限られているにもかかわらず、DBから多くの投稿を取得し、その後PHP側で必要な件数まで絞り込んでいる箇所がありました。

また、ユーザーページでは、

1. 投稿IDをすべて取得する
2. PHP側で投稿数を数える
3. 投稿IDを `IN (...)` に並べる
4. コメント数を取得する

という処理が行われていました。

そのため、

- DBからPHPへ転送するデータ量
- PHP側で処理するデータ量
- 不要なSQL処理

を減らせると考えました。

## 改善内容

### 1. トップページの投稿取得

トップページでは、有効なユーザーの投稿だけをSQL側で絞り込み、画面表示に必要な件数だけ取得するようにしました。

主に以下の処理を追加しました。

```sql
INNER JOIN users
WHERE users.del_flg = 0
LIMIT POSTS_PER_PAGE
```

これにより、不要な投稿をPHP側へ送らないようにしました。

### 2. `/posts` の追加読み込み

追加読み込みでも同様に、

- 有効なユーザーの投稿だけを対象にする
- 取得件数を制限する

ように変更しました。

### 3. ユーザーページの投稿取得

ユーザーの投稿をすべて取得するのではなく、

```sql
LIMIT POSTS_PER_PAGE
```

を追加し、画面表示に必要な最新の投稿だけ取得するようにしました。

### 4. 投稿数の集計

変更前は投稿IDをPHP側へ取得してから `count()` していました。

これをMySQL側で直接集計するように変更しました。

```sql
SELECT COUNT(*) AS count
FROM posts
WHERE user_id = ?
```

### 5. 投稿についたコメント数の集計

変更前は投稿IDをすべて取得し、`IN (...)` を使用してコメント数を取得していました。

これを `posts` と `comments` のJOINによって直接集計するように変更しました。

```sql
SELECT COUNT(*) AS count
FROM comments c
INNER JOIN posts p
    ON c.post_id = p.id
WHERE p.user_id = ?
```

# 採用しなかった改善案

改善の途中で、投稿ごとのコメント数取得とコメント取得をまとめるために、

```sql
COUNT(*) OVER()
```

を使用する方法も試しました。

しかし、ベンチマークではスコアが安定せず、改善②より性能が低下する結果も確認されました。

そのため、この変更は採用せず、元の実装へ戻しました。

この検証から、SQLの発行回数を減らしたり処理をまとめたりすることが、必ずしも高速化につながるとは限らず、実際にベンチマークを測定して判断することが重要だと学びました。

# 今回意識したこと

今回の課題では、単にコードを書き換えるのではなく、

1. ベンチマークを取得する
2. コードやSQLを確認してボトルネックを探す
3. 改善案を実装する
4. 再度ベンチマークを取得する
5. 変更前後を比較する
6. 結果が悪ければ変更を採用しない

という流れを意識しました。

特に改善③では、ベンチマークのばらつきを考慮し、変更前後を同じ環境で複数回測定して中央値を比較しました。

パフォーマンス改善では、予想だけで判断するのではなく、実際の計測結果をもとに変更を採用することの重要性を学びました。
